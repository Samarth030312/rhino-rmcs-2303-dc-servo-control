## ED-M1 — Where the P / I / PI controller lives (control-loop boundary)

**Status: DECIDED 2026-10-09 (owner: "you decide")**

### Facts that force the decision

- The RMCS-2303 always closes its own loop (HARDWARE_REFERENCE §2.1). There is no
  mode in which the Arduino sets armature voltage.
- The course asks to "use Arduino to control the motor 1) position, and 2) speed" and to
  "apply various functions available … explore P, I and PI" (SRC-001, p.33).
- The drive exposes its own position P and I gains (registers 4 and 6) and a velocity
  feed-forward gain (register 8), with unknown scaling and unknown effect in speed mode.
- Feedback reaches the Arduino only through Modbus at 9600 baud (§2.8).

### Options

| | Option | P/I/PI evaluated on | Plant seen by the controller |
|---|---|---|---|
| A | **Drive-internal loops** | Drive registers PPG (P) and PIG (I) in Mode 2 | Motor + load |
| B | **Arduino outer loop around drive speed mode** | Arduino code | Drive speed loop + motor + Modbus delay |
| C | Bypass the drive (MOSFET/H-bridge, course week-5 parts list) | Arduino code | Bare motor |

### Choice

**B as the primary experiment, A as a secondary hardware exploration, C in simulation only.**

- **B** is the only option where the P, I and PI laws are code we write, can read, and can
  simulate faithfully. It produces the textbook results the course questions ask for:
  - Speed loop: P leaves a steady-state error `e_ss = r / (1 + Kp)`; I removes it; PI does both.
  - Position loop: the drive's speed loop makes the plant an integrator, so P already gives
    zero step error; I alone oscillates; PI trades overshoot for load rejection.
- **A** uses "the functions available" in the drive. We can run it on hardware and record
  it, but we cannot simulate it honestly: the drive's internal structure and gain scaling
  are undocumented. The app does **not** pretend to simulate it.
- **C** is what the course's week-4 simulation (CTMS motor model) and week-5 parts list
  describe. Our hardware is different. We keep it as the "Bare DC motor" plant in the
  simulation so the Simulink assignment is satisfied, with RMCS-5032 parameters (ESTIMATED).
  We do not build it in hardware: driving a 7.5 A motor from a bench MOSFET is out of scope.

### Consequences

- Outer-loop sample time is bounded by Modbus traffic. Estimate at 9600 baud, 10 bits/char:
  speed loop = write SPD (17+17 chars) + read speed (17+15) ≈ 66 chars ≈ **69 ms**;
  position loop adds two more reads ≈ **135 ms**. Defaults: Ts = 0.10 s (speed) and
  0.15 s (position), labelled ESTIMATED until MOTOR-02 measures the real cycle time.
  Measured on the rig 2026-10-25 (firmware DIAG, `hw_session_20261025-000324.log`): the whole
  sample takes 70.5 ms (speed, drive register), 74.8 ms (speed, encoder) and 78 ms (position;
  110 ms when the direction word is written too), with no overruns. The position loop reads one
  register pair, not two: the 135 ms estimate was too high. Both sample times keep their margin.
- Commands are magnitude + direction (register 14 unsigned, direction in register 2).
  A sign change costs an extra write.
- A load disturbance is first fought by the drive's own speed loop. Outer-loop P vs PI
  differences under load will be smaller on the rig than on the bare motor. That is a
  result to report, not a defect.

### What would reverse it

- The vendor library or drive firmware turns out to document the internal loop well
  enough to simulate A → add A to the simulation.
- The Modbus cycle measured in MOTOR-02 exceeds ~0.3 s → outer position loop becomes
  impractical; fall back to A for position.

## ED-M2 — Where the encoder is read

**Status: DECIDED 2026-10-09.** Read position and speed **from the drive over Modbus**, not by wiring
the encoder to the Uno.

Reason: at full speed the base encoder produces 15 600 counts/s. The Uno's interrupt pins
D2/D3 are the SoftwareSerial pins in the vendor wiring, and SoftwareSerial disables
interrupts while receiving each byte (~1 ms at 9600 baud), so direct counting would
lose counts. The drive already counts in hardware.

## ED-M3 — Simulation in base MATLAB, Simulink model as a second view

**Status: DECIDED 2026-10-09.** The interactive app and the batch runner use base-MATLAB
discrete-time simulation (`+servolab/+motor/simulate.m`), because the app must run on any
machine with MATLAB and must reproduce the firmware loop (sample time, delay,
quantisation, saturation) exactly. A Simulink model of the same plant is generated by
`matlab/models/dc_motor/build_dc_motor_simulink.m` for the course's Simulink requirement,
and a test checks both give the same response.

## ED-M4 — Units at the interfaces

- Speed in **output-shaft rpm** in the app, telemetry, CSV and plots. Base rpm appears
  only where the drive register is written or read (×100).
- Position in **output-shaft degrees** in the app; **counts** (5200/rev) in telemetry and raw CSV.
- Error convention `e = setpoint − measurement`.

## ED-M5 — Drive UART on AltSoftSerial (D8/D9), not SoftwareSerial (D2/D3)

**Status: DECIDED 2026-10-09.** The vendor wiring uses SoftwareSerial on D2/D3. SoftwareSerial
disables interrupts for the whole of each byte (~1 ms at 9600 baud), during which the Uno's
hardware UART can overrun and drop bytes arriving from MATLAB at 115200 baud — including STOP.
AltSoftSerial uses a timer and leaves interrupts on; on the Uno its pins are fixed: RX = D8
(from drive TXD, pin 3), TX = D9 (to drive RXD, pin 2). Cost: PWM on D10 is unavailable.
Reversal: none needed unless a Mega (hardware Serial1) is used instead of the Uno.

## ED-M6 — Firmware implements Modbus ASCII itself

**Status: DECIDED 2026-10-09.** The vendor library uses `String` (heap fragmentation on a 2 KB
Uno), fixed `delay(50)` waits, prints to the USB serial port (which would corrupt protocol v1),
and decodes negative speed with 65535 instead of 65536. The firmware implements the same
framing (verified against that library, SRC-012) with fixed buffers, a 150 ms reply timeout,
LRC and echo checks. It is exercised against an emulated drive in `firmware/tests/`.
